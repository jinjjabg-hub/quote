## 0. 왜 만드는가

| | 내용 |
|---|---|
| 문제 1 | 사장님은 현장 작업 중이라 문의에 늦게 답한다 → 고객 78%는 **가장 먼저 답한 업체**를 고른다 |
| 문제 2 | 비대면 견적 뒤 **현장 추가요금 분쟁** |
| 해결 | 고객이 링크로 입력(사진·체크리스트 포함) → 사장님 단가표로 자동 계산 → 사장님 1탭 승인 발송 |
| 성격 | 플랫폼(중개)이 아니다. **사장님이 쓰는 도구**이고, 여러 업체가 각자 가입해서 쓰는 서비스다 |

### 성공을 재는 숫자 (모든 단계에서 기록·확인)
| 지표 | 정의 | 왜 |
|---|---|---|
| **첫 응답 시간** | 문의 → 고객이 링크를 받기까지 | 문제 1 |
| **견적 발송 시간** | 요청 접수 → 견적 발송까지 | 문제 1 |
| **계약 전환율** | 발송한 견적 중 계약확정 비율 | 매출 |
| **현장 추가요금 발생률** | 계약 건 중 현장에서 금액이 바뀐 비율 | 문제 2 |
| **추천 가입 비율** (운영 지표) | 신규 업체 중 추천 코드로 가입한 비율 | 이 서비스는 써본 사람의 추천으로 퍼진다 (12장) |

→ 2단계에서 사장님 화면에 위 4개를 보여주는 **"내 숫자"** 카드를 넣는다. 기능을 추가할지는 이 숫자를 보고 정한다.

## 1. 확정한 결정 3가지

| 결정 | 선택 | 이유 | 설계에 미치는 영향 |
|---|---|---|---|
| 누가 쓰나 | **여러 업체가 쓰는 서비스** | BNI 멤버 등 여러 사장님에게 제공하고, 나중에 구독료를 받을 수 있음 | 업체 ID를 계정 uid와 분리, 직원 계정, 요금제 칸 |
| 업종 | **한 업체가 여러 업종 가능** | 청소업체는 입주청소·에어컨·줄눈 등을 같이 하는 경우가 많음 | 업체 아래 **서비스 메뉴**, 서비스마다 단가표 |
| 다른 앱 | **독립 운영, 링크로만 연결** | 앱을 따로 팔 수 있어야 함. 하나가 고장 나도 다른 앱은 안전 | Firebase 프로젝트·코드·로그인을 공유하지 않음 |

## 2. 전체 그림

```
                  ┌─────────────── 유입 채널 (링크만 연결, 앱 독립) ───────────────┐
                  │ 카톡·문자·숨고 │ 사장님 홈페이지 │ DiCA 명함 │ 만두 채팅 │ QR │ 부재중 자동문자 │
                  └──────────────────────────────┬─────────────────────────────────┘
                                                 ▼
 ┌──────────────────────────────── 견적 서비스 (이 저장소) ────────────────────────────────┐
 │                                                                                        │
 │  [고객 화면]  q.html?s=업체주소 → 서비스 선택 → 단계형 입력 → 사진 → 제출               │
 │       │                                                                                │
 │       ▼                                                                                │
 │  [핵심 엔진] 업종 템플릿(JSON) + 업체 단가표 → calc.js(순수 함수) → 항목별 금액·조건     │
 │       │                                                                                │
 │       ▼                                                                                │
 │  [사장님 화면] 요청 목록 → 확인·수정 → 1탭 발송 → 상태 관리 → 내 숫자                   │
 │       │                                                                                │
 │       ▼                                                                                │
 │  [견적서] view.html?id= → 포함/불포함/⚠️조건 → 예약 요청 → (결제)                       │
 │                                                                                        │
 │  [서버 함수: Cloud Functions] 알림·문자·결제 확인·AI 분석: "돈·비밀키·외부 API"는 전부 여기 │
 └────────────────────────────────────────────────────────────────────────────────────────┘
```

### 계층 규칙 (코드가 엉망이 되지 않게 하는 핵심)
| 계층 | 하는 일 | 하면 안 되는 일 |
|---|---|---|
| **템플릿 (templates/*.json)** | 업종별 질문·체크리스트·계산 규칙·기본 단가 | 코드(함수) 넣기 |
| **엔진 (js/core/)** | 템플릿을 해석해 계산·검증. 순수 함수, 테스트 필수 | 화면·Firebase 접근 |
| **데이터 (js/data/)** | Firestore·Storage 읽고 쓰기를 한곳에서만 | 계산, 화면 |
| **화면 (js/pages/)** | 그리기와 클릭 처리 | 직접 계산 공식 쓰기, 업종 이름으로 if 분기 |
| **서버 함수 (functions/)** | 비밀키·결제·외부 API·알림 | 화면 |

> 금지 1: **화면 코드에 `if (업종 === '이사')` 같은 분기를 넣지 않는다.** 업종 차이는 전부 템플릿으로 표현한다.
> 금지 2: **외부 서비스 키를 브라우저 코드에 넣지 않는다.** 전부 서버 함수에 둔다.

### v1 → v2에서 바뀌는 것과 이유
| v1 (지금) | v2 | 이유 |
|---|---|---|
| shopId = 사장님 uid | shopId = 랜덤 + `members` | 직원 계정, 업체 양도, 1인 여러 업체 |
| 링크 `?shop=긴uid` | `?s=slug` | 명함·문자에 넣기 좋은 짧은 주소 |
| 업체당 템플릿 1개 | `services[]` + 서비스별 단가표 | 여러 업종 |
| 단가표 1개 | `pricing/{serviceId}` | 서비스마다 단가가 다름 |
| 상태만 기록 | 단계별 시각 + 유입 경로 | 성공 지표를 데이터로 확인 |
| 날짜 자유 입력 | 가능한 날 중 1·2순위 선택 + 가예약 | 일정 조율 연락 제거 (9장) |
| (없음) | `plan`, `referral`, `members` 역할, 견적의 `labor` | 나중에 붙일 기능의 **칸만 미리** (기능은 단계별로) |

**전환 시점: 지금.** 실제 고객 데이터가 쌓이기 전이라 옮길 데이터가 거의 없습니다. 실사용이 시작된 뒤에 바꾸면 비용이 몇 배로 듭니다.

## 4. 계산 엔진 v2: 업종을 템플릿만으로 추가하기

지금 공식 `max(최소, 기본 금액) × (1+할증%) + 옵션`은 그대로 두고, **"기본 금액"을 만드는 방식만 늘린다.** ✅ 3가지 구현됨 (`js/calc.js computeBase`)

| base.type | 계산 | 업종 (템플릿) |
|---|---|---|
| `perUnit` ✅ | 수량 × 단가 (최소 금액) | 입주청소(평) |
| `itemized` ✅ | Σ(항목 수 × 종류별 단가), `bySize` 항목은 × 크기, 선택적으로 항목당 설치비 | 에어컨(대수), 줄눈·탄성(부위·평), 커튼(창마다 폭) |
| `composite` ✅ | 구성요소의 합. 구성요소 종류: `select`(선택값별 단가) · `perUnit`(수량×단가, 무료 수량) · `tier`(구간: 금액 또는 앞 금액의 %) · `fixed`(조건부 고정) | 중문(제품+사이즈 구간%+유리+철거), 이사(차량+형태+추가 인원+거리 구간+계단+사다리차) |

처음 계획한 `product` 방식은 `composite`로 충분히 표현돼서 따로 만들지 않았다 (엔진을 작게 유지).

그 외 엔진 기능 ✅
- **범위 견적:** 템플릿 `quoteMode: "range"` + `rangePct` → 결과에 `range.low~high` (커튼 ±15%, 중문 ±10%, 이사 ±15%)
- **인력 예상:** 템플릿 `labor` → `estimateLabor()` 가 "○명 × ○시간" 계산 (10장 일정·인력 관리의 기초)
- **조건부 옵션:** 옵션에 `when` 이 있으면 조건이 맞을 때만 자동으로 켜짐 (예: 에어컨 완전분해 선택 시 대수 × 추가금)
- **날짜 파생값:** `$month`(성수기), `$monthEnd`(이사 월말) 추가
- **템플릿 점검:** `lintTemplate()` 이 흔한 실수를 찾아냄 (질문에 없는 필드, 단가 기본값 누락, 없는 옵션 참조 등). 모든 템플릿은 점검 오류 0건이어야 한다 (단위 테스트로 강제)

공통으로 계속 쓰는 것: 할증(%), 옵션(원), 체크리스트 → ⚠️조건, 포함/불포함, 1,000원 반올림, 계약금.

### 템플릿에 추가할 입력 형태
| 필드 type | 용도 | 예 |
|---|---|---|
| `items` (반복 입력) ✅ 엔진·시뮬레이터 / 고객 화면은 2단계 | 같은 질문을 여러 개 | 에어컨 3대(종류 선택), 창문 4개(폭) |
| `distance` | 출발·도착 주소 → 거리 구간 | 이사 |
| `select-product` | 제품 카드 선택(사진+가격대) | 중문 종류 |
| `showIf` (모든 필드에 붙는 조건) ✅ | 앞 질문의 답이 맞을 때만 보임. 문법은 `when`과 같음. 숨겨진 답은 계산에서 빠짐(`pruneHidden`), 질문이 모두 숨겨진 단계는 건너뜀 | 붙박이장 "있어요" → 개수 질문 |

### 템플릿 버전 규칙
- 템플릿마다 `version`이 있고, 요청에 `templateVersion`을 저장한다. 그래야 템플릿을 고쳐도 옛 견적이 깨지지 않는다.
- 새 업종 추가 = **JSON 1개 + 테스트 1개.** 엔진 코드를 고쳐야 한다면 base.type이 부족하다는 뜻이고, 그때만 엔진에 type을 추가한다.

## 4-1. 가입·업종 설정 (온보딩)과 업종별 결정사항

### 사장님 가입 흐름
```
구글 로그인 → 업체 기본정보(상호·연락처·영업지역·만두 ID)
  → 업종 선택(여러 개) → 업종별 설정 마법사(업종마다 4화면: 가격 기준 · 할증 · 옵션 · 정책)
  → 샘플 견적 미리보기(내 단가로 계산 결과 확인) → 내 견적 링크 발급(q.html?s=slug)
```
- 마법사 화면은 **템플릿의 `setup` 칸을 읽어서 자동으로 그린다.** 업종을 추가해도 마법사 코드는 고치지 않는다.
- 모든 칸에 시세 기준 기본값을 채워 두어, 사장님은 다른 숫자만 고치게 한다. 시세 경고는 `pricing.warnings`에 둔다.
- 업종은 가입 후에도 설정에서 추가하거나 끌 수 있다(`shops.services[].enabled`).

### 공통 결정 (업체당 1번, 업종별로 덮어쓰기 가능)
영업 지역·요일·시간대 / 부가세 포함 여부 / 견적 유효기간 / 계약금 % / 취소 규정 / 결제 수단 / 출장비 기준

### 견적 형태: 업종마다 가장 큰 차이
| quoteMode | 의미 | 업종 |
|---|---|---|
| `fixed` | 사진·체크리스트로 금액 확정 | 입주청소, 에어컨, 줄눈·탄성 |

### 템플릿에 추가되는 칸
```json
{
  "quoteMode": "fixed | range",
  "setup": {
    "groups": [
      { "title": "가격 기준", "fields": ["unitPrice", "minPrice", "areaBasis"] },
      { "title": "할증", "fields": ["surcharges.*"] },
      { "title": "옵션", "fields": ["options.*"] },
      { "title": "정책", "fields": ["policy.*"] }
    ]
  },
  "sample": { "customer": { "name": "테스트 고객" }, "answers": { "area": 34, "isNew": true }, "checklist": { "mold": "yes" } }
}
```
템플릿 최상위의 `sample`(샘플 고객 입력값)은 마법사 마지막의 "샘플 견적 미리보기"와 **테스트 모드**(아래 "테스트 모드")에 같이 쓰인다. ✅ 입주청소 템플릿에 추가됨

### 템플릿 `labor`: 이 견적이 몇 명 × 몇 시간인가 (일정 계산용)
```json
"labor": {
  "baseManHours": { "perUnit": 0.27, "min": 6 },          // 입주청소: 평당 0.27인시간, 최소 6인시간
  "adjust": [ { "when": {"field":"isNew","equals":true}, "pct": 20 },
              { "option": "mold", "manHours": 2 } ],
  "crew": { "min": 2, "max": 5, "maxHoursPerDay": 8 }      // 인원을 늘려 하루 안에 끝내는 규칙
}
```
업종 기본값은 템플릿이, 업체별 수정값은 `pricing/{serviceId}.labor` 가, 실제 기록 기반 보정은 서버 함수가 맡는다.

### 테스트 모드 ✅ (구현됨)
사장님이 실제 고객 없이 견적 흐름 전체를 직접 해보는 기능. 첫 세팅 직후 "내 단가로 견적이 어떻게 나가는지" 확인하는 용도이고, 협력 업체 시연에도 쓴다.

| 기능 | 동작 |
|---|---|
| 샘플 요청 1건 만들기 | 템플릿 `sample` 값 + 희망일 7일 뒤로 요청 생성 (`test: true`) |
| 고객 화면으로 직접 입력해보기 | `q.html?shop=…&test=1` → 고객 화면 상단에 테스트 표시, 요청에 `test: true` |
| 표시 | 목록 "테스트" 배지, 상세·고객 화면·견적서 상단 보라색 안내 |
| 지우기 | 테스트 요청 + 그 견적서 + 사진을 한 번에 삭제 (실제 요청은 그대로) |

규칙: **테스트 데이터는 지표("내 숫자")·크레딧 차감·알림톡 발송에서 항상 제외한다.** 새 기능을 만들 때 `test` 여부를 반드시 확인한다.

## 4-2. 개발자 모드 ✅ (구현됨)

**왜:** 운영자(대표)가 코드 없이 모든 업종의 작동 과정을 직접 보고, 오류가 나면 원인을 보고 판단할 수 있어야 한다.

| 기능 | 주소 | 하는 일 |
|---|---|---|
| **업종 시뮬레이터** | `dev.html` (로그인 불필요) | 업종 탭 → ① 고객 입력(템플릿 질문 그대로) ② 계산 결과(항목·할증·옵션·합계·범위·계약금·⚠️조건·포함/불포함·인력 예상) ③ 사장님 수동 조정 ④ 단가표 편집(템플릿 기본값 모양대로 자동 생성) ⑤ 원본 데이터(JSON 복사). 저장되지 않음 |
| **오류 패널** | 아무 화면 주소 뒤 `?dev=1` (이 기기에 기억) · 끄기 `?dev=0` · 사장님 화면 > 업체 정보 > 개발자 모드 | 화면 왼쪽 아래 🛠 버튼. 오류·경고·정보를 시간순으로 모으고 "전체 복사"로 그대로 전달. 페이지·Firebase 프로젝트·브라우저 정보 포함 |
| 템플릿 점검 | 시뮬레이터 상단 | `lintTemplate()` 결과. 오류가 있으면 오류 패널에도 기록 |

원칙:
- 시뮬레이터는 **실제 앱과 같은 `calc.js`·`templates/*.json`** 을 쓴다. 시뮬레이터에서 맞으면 실제 계산도 같다.
- 오류 패널은 꺼져 있으면 아무것도 하지 않는다 (고객 화면 성능·개인정보 영향 없음). 기록은 브라우저 안에만 있고 서버로 보내지 않는다.
- 새 업종·새 계산 방식은 **시뮬레이터에서 먼저 확인**한 뒤 실제 화면에 붙인다.

## 4-4. 주소로 평수 자동 조회 ✅ 구현 (배포·팍스타운 검증 후 공개)

**왜:** 고객이 전용면적과 공급면적을 헷갈려 평수를 잘못 쓰면 견적이 틀리고, 현장에서 금액이 바뀌어 분쟁이 된다. 공공데이터로 평수를 잡아주면 이 원인이 사라진다.

| 단계 | 데이터 | 하는 일 |
|---|---|---|
| ① | 행정안전부 **도로명주소 검색 API** | "가야대로 팍스타운" → 단지 선택 → 건물관리번호(시군구·법정동·번지) |
| ② | 국토교통부 **건축HUB 건축물대장 전유공용면적** | 동·호 → 전용면적·공용면적 |
| ③ | 계산 | 공급면적(전용 + 주거공용) → 평 → 고객 화면에 "전용 84.9㎡ · 약 34평 맞나요?" 확인 |

- 호출은 **서버 함수**(`functions/areaLookup`)에서만. 인증키는 서버 비밀값으로 보관 (브라우저 노출 금지)
- 공용면적에 주차장 등 기타공용이 섞일 수 있어 **공급면적 계산 규칙은 실제 단지로 검증** (첫 검증: 부산 가야대로 팍스타운)
- 조회 실패(빌라·주택 대장 불일치, 신축 미등재) 시 **직접 입력으로 자연스럽게 넘어감**
- 조회 결과는 요청에 `areaSource: 'registry' | 'manual'` 로 남겨 정확도를 데이터로 확인
- 준비물: 공공데이터포털(data.go.kr) 회원가입 → 두 API **활용신청** → 인증키 (운영자가 직접) ✅ 완료

### 구현 (2026-10-25)
| 부분 | 파일 | 내용 |
|---|---|---|
| 서버 함수 | `functions/lib/areaLookup.js` | HTTP 함수 `areaLookup` (서울 리전). Secret Manager 의 `JUSO_SEARCH_KEY`·`JUSO_DETAIL_KEY`·`BLD_KEY` 를 **읽기만** 함. 허용 주소(우리 화면)에서 온 요청만 받음 |
| 계산 | `functions/lib/area.js` | ① 단지 검색 ② 동 ③ 호(상세주소 API) ④ 건축HUB 전유공용면적 → 공급 = 전용 + 주거공용. 주차장·관리사무소 등 기타공용은 제외 (`EXCLUDED_COMMON_RE`). 동·호 표기 차이("101동"/"101")는 차례로 다시 조회. 인증키는 인코딩·디코딩 어느 쪽이 저장돼 있어도 동작 |
| 화면 | `js/areaLookup.js` | 템플릿 숫자 질문에 `"lookup": "registry"` 가 있으면 "주소로 평수 찾기" 패널. 실패·응답 없음(10초)·결과 거절 → **직접 입력**으로. 평수 칸은 언제나 직접 고칠 수 있음 |
| 공개 | `js/config.js` `areaLookupConfig.enabled` | 실제 단지 검증 전에는 꺼둠. 켜기 전 시험: 고객 링크 + `&lookup=1`, 검증 화면: `dev.html` ⑥ (항목별 면적 표) |
| 배포 | `배포.md` ⑤ | Cloud Shell 에서 `deploy --only functions:areaLookup` |

**저장 (사장님 결정, 2026-10-25):** 요청 `answers` 에 `areaSource`('registry'|'manual')와 `areaLookup`(단지명·도로명주소·동·호·전용㎡·공급㎡·평)을 남긴다. 단지명·동·호는 **사장님 화면에만** 보이고 고객 공개 견적서(quotes)에는 복사하지 않는다. 고객이 대장 평수를 고치면 `manual` 로 바꾸고 대장 값은 비교용으로 남긴다 (정확도 지표).
> ⚠️ 동·호까지 저장하므로 개인정보 처리방침의 수집 항목에 "주소(단지명·동·호)"가 들어가야 한다 (운영자 확인).

## 4-5. 현장 인터뷰 기록 (협력 업체 검증)

### 입주청소 업체 대표 통화 (2026-10-24)

| 고객이 전화보다 비대면을 점점 선호한다. 얼굴을 못 본 단골도 있다 | 링크 견적 방향이 맞다 | 변경 없음 |
| 본인 홈페이지에 견적 프로그램을 얹고 싶어 한다 | 6-1장 임베드·위젯 수요 확인 | 2단계 우선순위 근거 |
| 끝난 뒤 합의한 내역을 정리해서 고객에게 보낸다 | 견적서가 곧 분쟁 방지 기록 | 변경 없음 (견적서 포함/불포함/조건) |

### 아직 반영하지 않은 것 (확인 필요)
- **거주 상태:** 신축 입주 / 이사 청소 / 거주 중 청소 구분. 지금은 `isNew`만 있다. 업체가 이 구분으로 단가를 다르게 받는지 확인 후 결정.
- **베란다 확장 여부, 외창(바깥쪽) 범위:** 외창은 옵션으로 있음. 확장 여부가 가격에 영향을 주는지 확인.
- **오염 요율 기준:** 15%·30%는 한 업체의 값이다. 다른 업체 검증 후 기본값 조정.
- **상업 공간·정기 청소 템플릿:** 방문 견적이 필수라 `range` + 방문 예약 흐름(3단계) 이후.

### 6-1. 유입 채널: 같은 견적 링크를 어디에 붙이나
모든 채널은 **같은 고객 화면**(`q.html?s=slug`)을 쓰고, 뒤에 `&ch=유입경로`만 붙인다. 채널마다 화면을 따로 만들지 않는다.

| 채널 | 방식 | `ch` | 비고 |
|---|---|---|---|
| 카톡·문자·숨고 채팅 | 링크 붙여넣기 | `link` | ✅ 지금 가능 |
| **사장님 홈페이지: 버튼** | "견적 받기" 버튼에 링크 | `homepage` | 어디든 가능 |
| **사장님 홈페이지: 끼워넣기(임베드)** | 코드 한 줄 → 페이지 안에 견적창 | `homepage` | 아임웹·Wix·카페24 등 HTML 코드를 넣을 수 있는 곳 |
| **사장님 홈페이지: 떠 있는 버튼(위젯)** | 코드 한 줄 → 구석의 "견적 받기" 버튼이 견적창을 엶 | `homepage` | 위와 같음 |
| 네이버 스마트플레이스·블로그 | 링크만 (외부 코드 불가) | `naver` | |
| 인스타그램 프로필 | 링크만 | `insta` | |
| 전단지·차량 스티커·현장 안내문 | **QR 코드** (사장님 화면에서 생성·다운로드) | `qr` | |
| DiCA 명함 | "견적 받기" 버튼 | `dica` | 앱 독립 원칙: 링크로만 |
| 만두 | 채팅 버튼 ↔ 견적 링크 | `mandu` | ✅ PR #3 |
| 부재중 자동문자 | 전화 앱이 링크 발송 | `missed_call` | 외부 설정 안내 |

**끼워넣기 모드** (`&embed=1`): 고객 화면 코드를 그대로 쓰고 아래만 바꾼다. 작업량이 적다.
- 상단 업체 로고·이름은 숨긴다 (홈페이지에 이미 있음)
- 내용 높이를 부모 페이지에 알려 높이를 자동으로 맞춘다 (`postMessage`)
- 위젯은 `widget.js` 한 파일. 버튼을 그리고, 누르면 임베드 창을 연다

**유입 경로별 지표:** "내 숫자"에 채널별 요청 수와 계약 전환율을 보여준다. 사장님이 광고·홍보를 어디에 할지 정하는 근거가 된다.

**사장님 화면 "링크 붙일 곳" 안내** (가입 마법사 마지막 + 설정 메뉴): 채널별 복사 버튼, 홈페이지 코드 복사, QR 다운로드, 채널별 붙이는 방법.

> 원칙 유지: 사장님 홈페이지·QR로 들어온 고객도 **그 업체만** 본다 (11장 절대 규칙).

## 9. 일정: 누가 날짜를 정하나

**결정: 사장님이 받을 수 있는 날을 정해두고 → 고객이 그 안에서 고르고 → 사장님이 확정한다.**

| 방식 | 문제 |
|---|---|
| 고객 자유 선택 (MVP) | 이미 찬 날을 고르면 다시 연락해서 조율해야 함 → 응답이 늦어짐 |
| 사장님 통보 | 고객이 기다리고 안 맞으면 다시 조율 → "가장 먼저 응답"이 무너짐 |
| **혼합 (채택)** | 고객은 가능한 날만 보고, 사장님은 승인만. 조율 연락이 사라짐 |

흐름:
1. **사장님(가입 시):** 영업 요일·시간, 하루 최대 건수(또는 직원 수), 쉬는 날
2. **고객:** 달력에서 가능/마감을 보고 **1·2순위**를 고름. 할증일(주말·손 없는 날)은 `+10%`로 표시해 평일 선택을 유도
3. **사장님(발송 시):** 1·2순위 중 하나로 견적 발송. 둘 다 안 되면 다른 날 제안
4. **고객 예약 요청 → 가예약** (예: 24시간 `holdUntil`). 계약확정 또는 계약금 결제 시 확정 예약
- 시간 단위는 **오전 / 오후 / 종일**. 현장 작업은 정확한 분 단위가 아니라 반나절 단위로 움직임
- 범위 견적 업종은 **실측·방문 예약(30~60분)** 과 **작업일**을 따로 잡음
- 개인정보: 고객 달력은 `public/availability`(날짜별 남은 자리)만 읽음. 다른 고객 예약은 볼 수 없음

## 10. 일정·인력 관리 (팀 요금제)

직원이 여러 명인 업체는 "하루 몇 팀"이 아니라 **"몇 명 × 몇 시간"** 으로 계산해야 한다.
(예: 직원 10명이면 같은 시간에 2명×3시간 작업 3건과 3명×3시간 작업 1건이 동시에 가능, 5명×6시간 작업은 5명이 6시간 비어 있어야 가능)

### 역할 분담: 계산은 규칙, AI는 예측 보정
| 부분 | 담당 | 이유 |
|---|---|---|
| 이 견적이 몇 명 × 몇 시간인가 | 템플릿 `labor` 규칙 → **AI가 실제 기록으로 보정** | 업체·현장마다 달라서 데이터로 정확해짐 |
| 그 인원이 그 시간에 비어 있나 | **정확한 계산 (규칙)** | 일정은 틀리면 중복 예약 사고. AI 추측 금지 |
| 고객 달력의 가능 시간 | 위 두 결과로 자동 계산 | **고객마다 청소 규모에 맞게 다르게 보임** (작은 청소는 가능, 큰 청소는 마감) |

### 범용 설정 원칙: "설정은 업체가, 기본값은 우리가, 보정은 데이터가"
업체마다 다른 운영 방식은 우리가 정하지 않고 **설정 칸**으로 만든다. 같은 코드에 설정만 다르게 동작한다.

| 설정 | 선택지 | 기본값 |
|---|---|---|
| 일정 관리 | 끄기(날짜만) / 켜기 | 끄기 (1인 사장님) |
| 배정 방식 | 고정 팀 / 매번 조합 | 매번 조합 |
| 이동 시간 | 고정 N분 / 주소로 계산(나중) | 60분 |
| 근무 시간 | 업체 기본 + 직원별 예외 | 08~18시 |
| 인력 계산 | 업종 기본 → 업체 수정 → 실제 기록 보정 | 템플릿 `labor` |
| 투입 인원 | 최소~최대 | 2~5명 |

### 화면
| 누가 | 화면 | 하는 일 |
|---|---|---|
| 사장님 | 일정표 (직원 × 시간) | 자동 배정 확인, 끌어서 직원 변경 |
| 사장님 | 직원 관리 | 근무 요일, 휴무일, 가능 업무 |
| 직원 | 오늘 내 현장 (폰) | 주소·시간·체크리스트 → 시작/완료 → 완료 사진 (→ `actuals` 기록) |
| 고객 | 달력 | 내 청소 규모에 맞는 가능 날짜·시간대만 표시 |

AI 보정은 실제 기록이 **업체당 30~50건** 쌓인 뒤부터 의미가 있다. 그 전에는 업체가 정한 기준으로 동작한다.

## 11. 사용자 여정 (앱으로 쓰는 과정)

**원칙: 앱을 설치하는 사람은 사장님(과 직원)뿐이다. 고객은 링크만 연다.** 견적 한 번 받으려고 앱을 설치하는 고객은 거의 없다.

### 사장님
| 단계 | 하는 일 | 이탈을 막는 장치 |
|---|---|---|
| ① 알게 됨 | BNI 발표, DiCA 명함 고객 소개, 다른 사장님 추천 | 추천 코드 (양쪽 혜택) |
| ② 설치·가입 | 홈 화면 추가 또는 플레이스토어 → 구글 로그인 (1분) | 가입 양식 없음 |
| ③ 첫 세팅 | 업체 정보 → 업종 선택 → 마법사 → 샘플 견적 (10분) | 기본값이 채워져 있음, 중간 저장 |
| ④ 첫 링크 공유 | 카톡 프로필·명함·만두·전화 자동응답에 링크 등록 | 마법사 끝의 "링크 붙일 곳" 체크리스트 |
| ⑤ 매일 쓰기 | 🔔 새 요청 → 확인 → 1탭 발송 → 계약요청 → 확정 | **푸시 알림** (없으면 앱을 안 연다) |
| ⑥ 효과 확인 | "내 숫자": 견적 수, 평균 발송 시간, 계약률 | 숫자가 보여야 계속 쓴다 |
| ⑦ 유료 전환 | 무료 한도 초과 또는 팀 기능 필요 | 쓸모를 체감한 뒤에 한도에 닿게 설정 |
| ⑧ 추천 | 다른 사장님에게 추천 코드 공유 | ①로 순환 |

### 고객 (설치 없음)
문의 → 링크 받음 → 서비스 선택·질문·사진 (3분) → 대기 → 견적서(카톡·문자 링크) → 가능한 날 선택·예약 요청 → (계약금) → 작업 후 후기 요청

### 운영자 (우리)
업종 템플릿 추가·검증 / 전체 지표(업체 수·견적 수·전환율·이탈 지점) / 문의 응대(만두 채팅) / 요금 관리

### 고객 앱과 업체 선택: 하지 않는다
고객이 앱을 설치해 여러 업체 중에서 고르는 기능(중개 플랫폼)은 **만들지 않는다.**

| 이유 | 설명 |
|---|---|
| 사장님 이익과 충돌 | 손님은 사장님이 직접 데려온다(내 링크). 고객 화면에 경쟁 업체가 보이면 사장님은 링크를 안 뿌리고 구독도 안 한다 |
| 설치할 이유가 약함 | 입주청소·이사는 몇 년에 한 번. 드물게 쓰는 서비스 때문에 앱을 두는 고객은 거의 없다 |
| 다른 사업 | 업체 심사·리뷰·분쟁 중재·노출 경쟁·고객 모집 광고비가 필요하고, 숨고·당근 같은 강자가 있다 |

대신 원칙을 지키면서 고객과의 관계를 이어가는 기능:
| 기능 | 내용 | 단계 |
|---|---|---|
| 고객 "내 견적함" | 받은 견적서·예약 내역을 링크 하나로 모아 봄. **자기가 이용한 업체만** 보임 | 3~4단계 |
| 재방문 알림 | 업종별 주기(에어컨 1년, 줄눈 AS 기간 등)에 맞춰 **그 업체 이름으로** 알림톡 | 3단계 |
| 업체 간 소개 | 사장님이 **직접 고른 협력 업체**를 고객에게 소개 (예: 입주청소 → 줄눈). BNI 리퍼럴 방식 | 나중에 |

> **절대 규칙: 사장님 링크로 들어온 고객에게는 다른 업체를 보여주지 않는다.**
> 가입 업체가 충분히 많아져 "업체 찾기"를 검토하게 되더라도, 별도 서비스로 만들고 이 규칙은 그대로 지킨다.

### 배포 순서
| 방식 | 비고 |
|---|---|
| 1) 웹앱 "홈 화면에 추가" | 지금 가능. 아이폰은 홈 화면에 추가해야 푸시가 옴 (iOS 16.4 이상) |
| 2) 플레이스토어 (TWA) | 만두에서 쓴 방식(`MANDU/README-TWA.md`) 재사용. **조건부: "설치가 어려워 그만두는 사장님" 데이터가 보일 때** |

## 12. 요금제·크레딧·성장

### 요금 흐름: 써보기 → 쓴 만큼 → 내 사용량을 보고 월정액
처음 쓰는 사장님은 한 달 수요를 모른다. 그래서 **고정 월정액부터 팔지 않는다.**

| 단계 | 방식 | 이유 |
|---|---|---|
| ① 무료 체험 (`trial`) | **처음 10건 무료** | 돈 없이 효과 확인 |
| ② 충전형 (`credit`) | 크레딧을 사서 **쓸 때마다 차감**. 묶음이 클수록 건당 저렴 | 수요가 불확실해도 손해 없음 |
| ③ 월정액 추천 | 2~3개월 뒤 앱이 사용 기록으로 자동 제안: "지난 3개월 평균 월 28건 → ○○ 월정액이 충전보다 월 ○원 저렴" | 사장님이 **자기 데이터**로 결정 |
| ④ 월정액 | 3단계, 한도 초과분은 크레딧 차감 | 고정비로 관리. 충전형 유지도 허용(비수기가 긴 업종) |

- 월정액의 건당 가격이 충전형보다 싸게 설계한다 (자연스럽게 넘어오도록).
- 가격 숫자는 협력 업체 단계의 실제 사용량을 보고 정한다.

### 요금제 이름 (임시안: 앱 이름이 정해지면 톤을 맞춤)
영어(베이직·스탠다드·프로) 대신 **규모가 바로 보이는 한국어 이름**을 쓴다.

| 이름 | `plan` | 대상 | 포함 |
|---|---|---|---|
| 체험 | `trial` | 처음 가입 | 10건 무료 |
| 충전 | `credit` | 수요 파악 중 | 쓴 만큼 차감 |
| **혼자** | `solo` | 1인 사장님 | 월정액 · 여러 업종 · 알림 · 계약금 결제 |
| **팀** | `team` | 직원 몇 명 | 혼자 + **일정·인력 관리, 직원 앱** |
| **회사** | `company` | 직원 많은 업체 | 팀 + 직원 수·견적 수 확대, AI 시간 예측 |

일정·인력 관리가 상위 요금제인 이유: 필요한 업체만 쓰고(1인에게는 화면만 복잡), 낼 수 있는 업체이며(일정 실수 한 번의 손해가 구독료보다 큼), 비용이 실제로 더 든다(AI·직원 계정·지원).
기능 제한은 화면이 아니라 **서버·규칙에서** `plan`을 확인해 막는다. `plan`은 서버만 바꿀 수 있다.

### 무엇을 차감하나
| 행동 | 차감 | 이유 |
|---|---|---|
| **견적 발송** | **1크레딧** | 사장님이 직접 누른 순간이라 납득됨. 스팸 요청은 무시하면 비용 0. 같은 견적 수정 재발송은 추가 차감 없음 |
| 고객 요청 접수 | 차감 안 함 | 장난·스팸에도 돈이 나가면 불만 |
| 계약확정 | 차감 안 함 | 차감을 피하려고 확정을 안 누르면 일정·지표 데이터가 망가짐 |
| 알림톡·문자 | 건당 소량 (예: 0.1) | 실제 발송 비용 |
| AI 사진 분석 | 건당 소량 | 실제 API 비용 |

차감은 **견적 발송 시 서버 함수가** 하고 `ledger`에 기록한다. 화면에서는 절대 차감하지 않는다.

### 크레딧 두 종류
| | 무료 크레딧 (체험·추천 보상) | 유료 크레딧 (구매) |
|---|---|---|
| 차감 순서 | **먼저** | 나중 |
| 유효기간 | 있음 (예: 6개월) | 약관에 따름 |
| 환불 | 불가 | 미사용분 환불 규정 필요 |
| 사용처 | 이 서비스 안에서만 (견적 발송·알림톡·AI·월정액 차감) | 같음 |

사장님 화면에는 합쳐서 "무료 7건 + 충전 23건 남음"으로 보여준다.
> ⚠️ 크레딧은 **현금 교환·양도·판매 불가**. 서비스 이용료 전용이어야 전자금융 관련 규제(선불전자지급수단 등) 부담을 피할 수 있다. 유료 크레딧의 환불·유효기간은 **도입 전 세무사·법률 확인** 필수.

### 추천 보상 (가입 추천 → 크레딧)
| 누가 | 언제 | 예시 | 이유 |
|---|---|---|---|
| 추천받은 업체 | **가입 즉시** | 무료 10건 + 추천 보너스 5건 | 추천 코드를 넣을 이유 |
| 추천한 업체 | 추천받은 업체가 **견적 5건을 실제로 발송했을 때** | 10건 | 가입만으로 주면 가짜 가입이 생김. 실사용 시작 시점에 지급 |

안전장치: 사업자번호 또는 휴대폰 인증 1회(자기 추천 방지) · 추천 보상 월 한도(예: 월 5곳) · 지급은 서버만.
숫자는 예시이며 협력 업체 단계에서 조정한다.

### 고객 쿠폰 (각 업체 ↔ 그 업체 고객)
고객은 앱이 없고 몇 년에 한 번 이용하므로 포인트가 아니라 **쿠폰**을 쓴다. 쿠폰은 **각 업체가 만들고 그 업체에서만** 쓰인다(다른 업체 쿠폰 노출 없음).

| 쿠폰 | 예시 | 효과 |
|---|---|---|
| 지인 소개 | 친구 소개로 계약하면 둘 다 할인. 소개한 고객의 링크(`ch=friend`)로 자동 기록 | 고객 입소문 |
| 재방문 | 에어컨 1년 뒤 재방문 알림에 할인 | 단골 |
| 평일 할인 | 일정 달력에서 한가한 날 선택 시 할인 | 사장님 일정이 고르게 채워짐 |

### 성장: 이 서비스는 써본 사람의 추천으로 퍼진다
| 장치 | 내용 |
|---|---|
| 자랑할 숫자 | "내 숫자": 견적 수, 평균 발송 시간, 계약률. 추천은 "이걸로 계약이 늘었어"라는 말로 일어난다 |
| 추천 코드 | 위 추천 보상 |
| 업체 간 소개 | 소개받은 업체가 자연스럽게 서비스를 알게 됨. BNI 리퍼럴 구조 |
| 견적서 하단 표시 | "이 견적서는 ○○로 만들었습니다" (월정액은 끄기 가능) |
| 협력 업체 사례 | 초기 3~5곳의 전후 숫자를 BNI 발표 자료로 |

측정: 가입 시 "어떻게 알게 되셨나요?" + 추천 코드로 **추천 가입 비율**(0장 지표)과 추천받은 업체의 견적 5건 도달률을 본다. 도달률이 낮으면 추천이 아니라 첫 세팅 과정의 문제다.

### 피드백 받는 방식
| 대상 | 방식 | 반영 |

## 13. 작업 방식 (사람 ↔ AI)

| 단계 | 어디서 | 왜 |
|---|---|---|
| 1. 아이디어·방향 | 아무 데서나 | 생각을 넓히는 단계 |
| 2. 결정 전 검토 | **코드가 있는 곳 (Claude Code)** | 지금 구조로 되는지, 비용, 이미 있는 것을 코드로 확인 |
| 3. 결정 기록 | **이 문서** | 대화는 사라지지만 문서는 남는다. 다음 대화·다른 AI가 이어받음 |
| 4. 코딩 지시 | 짧은 지시문 | 예: "설계도 8장 1단계 진행. 완료 기준: ○○" |
| 5. 확인 | PR 1개 단위 | 테스트 통과 후 머지 |

- 주제가 바뀌면 새 대화로 시작하고, 첫 줄에 **"docs/설계도.md 읽고 시작"**.
- 의논만 한 날도 끝에 **"오늘 결정한 것 설계도에 반영"**.

## 14. 새 기능을 넣을 때 체크리스트

1. 이 기능은 **0장의 지표 중 무엇을 개선**하나? (답이 없으면 보류)
2. 이 문서의 **어느 계층·어느 단계** 칸인가? 칸이 없으면 이 문서부터 고친다
3. **업종에 따라 다른가?** → 템플릿으로. 화면 if 분기는 금지
4. **돈·비밀키·외부 API**인가? → 서버 함수로
5. 데이터 필드가 늘어나나? → 3장 표와 `firestore.rules`·규칙 테스트를 같이 고친다
6. 테스트: 엔진은 단위 테스트, 권한은 규칙 테스트, 흐름은 E2E
