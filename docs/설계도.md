# 견적 자동화 서비스: 전체 설계도 (v2)

> 이 문서가 **기준**입니다. 새 기능은 먼저 이 문서의 어느 칸에 들어가는지 정한 뒤 만듭니다.
> 칸이 없으면 코드보다 이 문서를 먼저 고칩니다. (README는 "지금 있는 것", 이 문서는 "가야 할 곳")

---

## 0. 왜 만드는가

| | 내용 |
|---|---|
| 문제 1 | 사장님은 현장 작업 중이라 문의에 늦게 답한다 → 고객 78%는 **가장 먼저 답한 업체**를 고른다 |
| 문제 2 | 비대면 견적 뒤 **현장 추가요금 분쟁** |
| 해결 | 고객이 링크로 입력(사진·체크리스트 포함) → 사장님 단가표로 자동 계산 → 사장님 1탭 승인 발송 |
| 성격 | 플랫폼(중개)이 아니다. **사장님이 쓰는 도구**이고, 여러 업체가 각자 가입해서 쓰는 서비스다 |

### 성공을 재는 숫자 (모든 단계에서 기록·확인)
| 지표 | 정의 | 왜 |
|---|---|---|
| **첫 응답 시간** | 문의 → 고객이 링크를 받기까지 | 문제 1 |
| **견적 발송 시간** | 요청 접수 → 견적 발송까지 | 문제 1 |
| **계약 전환율** | 발송한 견적 중 계약확정 비율 | 매출 |
| **현장 추가요금 발생률** | 계약 건 중 현장에서 금액이 바뀐 비율 | 문제 2 |

→ 2단계에서 사장님 화면에 이 4개를 보여주는 **"내 숫자"** 카드를 넣는다. 기능을 추가할지는 이 숫자를 보고 정한다.

## 1. 확정한 결정 3가지

| 결정 | 선택 | 이유 | 설계에 미치는 영향 |
|---|---|---|---|
| 누가 쓰나 | **여러 업체가 쓰는 서비스** | BNI 멤버 등 여러 사장님에게 제공하고, 나중에 구독료를 받을 수 있음 | 업체 ID를 계정 uid와 분리, 직원 계정, 요금제 칸 |
| 업종 | **한 업체가 여러 업종 가능** | 청소업체는 입주청소·에어컨·줄눈 등을 같이 하는 경우가 많음 | 업체 아래 **서비스 메뉴**, 서비스마다 단가표 |
| 다른 앱 | **독립 운영, 링크로만 연결** | 앱을 따로 팔 수 있어야 함. 하나가 고장 나도 다른 앱은 안전 | Firebase 프로젝트·코드·로그인을 공유하지 않음 |

## 2. 전체 그림

```
                  ┌─────────────── 유입 채널 (링크만 연결, 앱 독립) ───────────────┐
                  │ 카톡·문자·숨고 붙여넣기 │ DiCA 명함 "견적 받기" │ 만두 채팅 │ 부재중 자동문자 │
                  └──────────────────────────────┬─────────────────────────────────┘
                                                 ▼
 ┌──────────────────────────────── 견적 서비스 (이 저장소) ────────────────────────────────┐
 │                                                                                        │
 │  [고객 화면]  q.html?s=업체주소 → 서비스 선택 → 단계형 입력 → 사진 → 제출               │
 │       │                                                                                │
 │       ▼                                                                                │
 │  [핵심 엔진] 업종 템플릿(JSON) + 업체 단가표 → calc.js(순수 함수) → 항목별 금액·조건     │
 │       │                                                                                │
 │       ▼                                                                                │
 │  [사장님 화면] 요청 목록 → 확인·수정 → 1탭 발송 → 상태 관리 → 내 숫자                   │
 │       │                                                                                │
 │       ▼                                                                                │
 │  [견적서] view.html?id= → 포함/불포함/⚠️조건 → 예약 요청 → (결제)                       │
 │                                                                                        │
 │  [서버 함수: Cloud Functions] 알림·문자·결제 확인·AI 분석: "돈·비밀키·외부 API"는 전부 여기 │
 └────────────────────────────────────────────────────────────────────────────────────────┘
```

### 계층 규칙 (코드가 엉망이 되지 않게 하는 핵심)
| 계층 | 하는 일 | 하면 안 되는 일 |
|---|---|---|
| **템플릿 (templates/*.json)** | 업종별 질문·체크리스트·계산 규칙·기본 단가 | 코드(함수) 넣기 |
| **엔진 (js/core/)** | 템플릿을 해석해 계산·검증. 순수 함수, 테스트 필수 | 화면·Firebase 접근 |
| **데이터 (js/data/)** | Firestore·Storage 읽고 쓰기를 한곳에서만 | 계산, 화면 |
| **화면 (js/pages/)** | 그리기와 클릭 처리 | 직접 계산 공식 쓰기, 업종 이름으로 if 분기 |
| **서버 함수 (functions/)** | 비밀키·결제·외부 API·알림 | 화면 |

> 금지 1: **화면 코드에 `if (업종 === '이사')` 같은 분기를 넣지 않는다.** 업종 차이는 전부 템플릿으로 표현한다.
> 금지 2: **외부 서비스 키를 브라우저 코드에 넣지 않는다.** 전부 서버 함수에 둔다.

## 3. 데이터 구조 v2

```
users/{uid}                      로그인한 사장님·직원
  shopIds: [shopId]

shops/{shopId}                   업체 공개 정보 (shopId = 랜덤 ID)
  slug          고객 링크용 짧은 주소 (예: banjjak) → q.html?s=banjjak
  name, ownerName, phone, bizNo, logoUrl, manduId
  services: [{ id, templateId, title, enabled, order }]   서비스 메뉴 (공개)
  plan: 'free' | 'pro'           요금제 (서버만 변경)
  members: { uid: 'owner' | 'staff' }

shops/{shopId}/private/settings  비공개: 정책 기본값(유효기간·계약금·취소규정)
shops/{shopId}/pricing/{serviceId}   서비스별 단가표 (비공개)
shops/{shopId}/stats/daily_{yyyymmdd}  내 숫자 집계 (서버 함수가 기록)

slugs/{slug}                     slug → shopId (중복 방지)

templates/{templateId}           업종 템플릿 (관리자만 쓰기; 없으면 저장소 JSON)

requests/{requestId}
  shopId, serviceId, templateId, templateVersion
  status, customer{name,phone,region}, answers{}, items[] (반복 입력), checklist{}, photos[]
  channel: 'link'|'dica'|'mandu'|'missed_call'   유입 경로 (지표용)
  createdAt, firstViewedAt, sentAt, bookedAt, confirmedAt   지표용 시각

quotes/{quoteId}
  shopId, requestId, serviceId, 스냅샷(업체·고객·서비스), lines[], total, deposit,
  included[], excluded[], conditions[], policy, validUntil, verified, status
  payment: { status, amount, paidAt, provider }   서버 함수만 기록
```

### v1 → v2에서 바뀌는 것과 이유
| v1 (지금) | v2 | 이유 |
|---|---|---|
| shopId = 사장님 uid | shopId = 랜덤 + `members` | 직원 계정, 업체 양도, 1인 여러 업체 |
| 링크 `?shop=긴uid` | `?s=slug` | 명함·문자에 넣기 좋은 짧은 주소 |
| 업체당 템플릿 1개 | `services[]` + 서비스별 단가표 | 여러 업종 |
| 단가표 1개 | `pricing/{serviceId}` | 서비스마다 단가가 다름 |
| 상태만 기록 | 단계별 시각 + 유입 경로 | 성공 지표를 데이터로 확인 |

**전환 시점: 지금.** 실제 고객 데이터가 쌓이기 전이라 옮길 데이터가 거의 없습니다. 실사용이 시작된 뒤에 바꾸면 비용이 몇 배로 듭니다.

## 4. 계산 엔진 v2: 업종을 템플릿만으로 추가하기

지금 공식 `max(최소, 수량×단가) × (1+할증%) + 옵션`은 그대로 두고, **"기본 금액"을 만드는 방식만 4가지로 늘린다.**

| base.type | 계산 | 맞는 업종 |
|---|---|---|
| `perUnit` (현재) | 수량 × 단가 (최소금액) | 입주청소(평), 줄눈(m), 탄성코트(평) |
| `itemized` | Σ(항목 수 × 항목 종류별 단가) | 에어컨청소(벽걸이/스탠드/시스템), 커튼(창마다 폭·제품), 가전청소 |
| `product` | 선택한 제품 기본가 + 사이즈 구간 할증 | 중문, 방충망, 블라인드 시공 |
| `composite` | 여러 구성요소의 합 (거리 구간 + 층수 + 짐량 + 인원) | 이사, 폐기물 수거 |

공통으로 계속 쓰는 것: 할증(%), 옵션(원), 체크리스트 → ⚠️조건, 포함/불포함, 1,000원 반올림, 계약금.

### 템플릿에 추가할 입력 형태
| 필드 type | 용도 | 예 |
|---|---|---|
| `items` (반복 입력) | 같은 질문을 여러 개 | 에어컨 3대(종류 선택), 창문 4개(폭·높이) |
| `distance` | 출발·도착 주소 → 거리 구간 | 이사 |
| `select-product` | 제품 카드 선택(사진+가격대) | 중문 종류 |

### 템플릿 버전 규칙
- 템플릿마다 `version`이 있고, 요청에 `templateVersion`을 저장한다. 그래야 템플릿을 고쳐도 옛 견적이 깨지지 않는다.
- 새 업종 추가 = **JSON 1개 + 테스트 1개.** 엔진 코드를 고쳐야 한다면 base.type이 부족하다는 뜻이고, 그때만 엔진에 type을 추가한다.

## 5. 업종 로드맵

| 순서 | 업종 | base.type | 추가로 필요한 것 |
|---|---|---|---|
| ✅ | 입주청소 | perUnit | (완료) |
| 1 | 에어컨 청소 | itemized | `items` 입력 |
| 2 | 줄눈·탄성코트 | perUnit | 없음 (템플릿만) |
| 3 | 커튼·블라인드 | itemized | 치수 입력 |
| 4 | 중문 | product | 제품 카드 |
| 5 | 이사 | composite | 거리 계산 (서버 함수 + 지도 API) |

> 순서 원칙: 엔진을 덜 바꾸는 업종부터. 각 업종은 **실제 사장님 1명의 단가표·질문으로 검증**한 뒤 공개한다.

## 6. 외부 연동: 모두 "서버 함수 + 어댑터"로

| 기능 | 방식 | 어디서 | 단계 |
|---|---|---|---|
| 만두 채팅 | 링크 (`MANDU/?u=만두ID`) | 화면 | ✅ PR #3 |
| DiCA 명함 "견적 받기" | 링크 (`q.html?s=slug&ch=dica`) | DiCA 쪽 버튼 | 2단계 |
| 새 요청 알림 (사장님) | 웹 푸시(FCM) → 나중에 알림톡 | 서버 함수 onCreate(requests) | 2단계 |
| 부재중 자동문자 | 전화 앱/통신사 서비스가 링크 문자 발송 → 앱은 `ch=missed_call` 링크만 제공 | 외부 | 2단계 (설정 안내) |
| 견적 발송 알림 (고객) | 알림톡/문자 (발송 대행사 API) | 서버 함수 | 3단계 |
| 계약금 결제 | 토스페이먼츠 결제위젯 → 결제 확인은 **서버 함수만** `payment` 기록 | 서버 함수 | 3단계 |
| 미응답 재연락 | 예약 함수: 발송 후 N일 무응답이면 문자 | 서버 함수 | 3단계 |
| AI 사진 분석 | 요청 생성 시 분석 → `aiHints[]` → 사장님 화면에 "추가요금 후보" | 서버 함수 | 4단계 |
| AI 자동통화 | 외부 서비스(통화비서 등)가 링크 안내 | 외부 | 데이터를 보고 결정 |

**어댑터 원칙:** 문자 업체나 결제 업체를 바꿔도 `functions/adapters/sms.js` 한 파일만 바뀌게 한다.

## 8. 단계별 로드맵

| 단계 | 내용 | 끝났다는 기준 |
|---|---|---|
| **1. 기반 정리 (v2 구조)** | 폴더 분리, 데이터 v2(업체 ID·slug·서비스 메뉴·서비스별 단가표), 목록 최근 100건, 지표용 시각 기록, 규칙 v2 | 기존 테스트 + 새 규칙 테스트 통과, 입주청소 시나리오 그대로 동작 |
| **2. 업종 확장 + 알림** | 엔진 itemized → 에어컨 청소, 줄눈. 사장님 새 요청 푸시 알림. "내 숫자" 카드. DiCA 버튼 | 업체 1곳이 2개 업종으로 실제 견적 10건 |
| **3. 계약까지 닫기** | 고객 알림톡, 계약금 결제, 미응답 재연락 | 결제 1건 성공, 재연락으로 회수 1건 |
| **4. 판매 준비** | 요금제(무료/프로), 운영자 화면, App Check(스팸 방지), 커튼·중문 | 외부 업체 3곳 사용 |
| **5. 고도화** | 이사, AI 사진 분석, 단가표 역산 | 지표가 정체된 곳부터 |

> 각 단계는 PR 여러 개로 나누고, PR마다 테스트를 통과해야 합친다.

## 9. 새 기능을 넣을 때 체크리스트

1. 이 기능은 **0장의 지표 중 무엇을 개선**하나? (답이 없으면 보류)
2. 이 문서의 **어느 계층·어느 단계** 칸인가? 칸이 없으면 이 문서부터 고친다
3. **업종에 따라 다른가?** → 템플릿으로. 화면 if 분기는 금지
4. **돈·비밀키·외부 API**인가? → 서버 함수로
5. 데이터 필드가 늘어나나? → 3장 표와 `firestore.rules`·규칙 테스트를 같이 고친다
6. 테스트: 엔진은 단위 테스트, 권한은 규칙 테스트, 흐름은 E2E
