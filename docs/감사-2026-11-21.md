## 4. 치명적인 문제점 TOP 5

### ① 무료 10건 제한을 우회할 수 있다 (매출) — [확인]
- **현상 (경로 3개)**
  1. 견적서 생성 규칙은 `test == true`면 요금 검사를 건너뛴다. 그런데 `test` 값이 **요청(request)의 test 값과 같은지 확인하지 않는다.** 실제 고객 요청에도 `test: true` 견적을 만들 수 있다. (단, 고객 화면에 "테스트 견적서" 띠가 뜸)
  2. 견적서 수정(update) 규칙은 `shopId`만 확인한다. 이미 만든 견적서 1개의 `requestId`·`customer`·`lines`·`test`를 **계속 바꿔 쓰면** 새 문서가 안 생겨서 건수가 늘지 않는다.
  3. `canSend`는 화면이 `billingStatus`를 불러야 다시 계산된다(`handleStatus`). 부르지 않으면 상태 문서가 예전 값(`canSend: true`)으로 남아 있다.
- **원인**: 세는 일을 서버 트리거가 아니라 "화면이 부르는 함수"에 맡김.
- **지금 피해**: 없음. `config/billing.enforce`가 꺼져 있고 결제도 미개통. **결제를 여는 순간 문제가 된다.**
- **고치는 법**
  - 규칙: `create` 시 `request.resource.data.test == get(requests/…).data.get('test', false)`. `update` 시 `requestId`·`test`·`shopId` 변경 금지 (`affectedKeys()`에서 제외).
  - 서버: `quotes` `onDocumentCreated` 트리거로 `used`를 `FieldValue.increment(1)`, 한도에 닿으면 `canSend=false`. 화면 호출에 의존하지 않게.
- **난이도·시간 [추정]**: 낮음 · 0.5~1일 (에뮬레이터 규칙 테스트 포함)

### ② 고객 입력 화면에 개인정보 수집·이용 고지가 없다 (법적 위험) — [확인]
- **현상**: `q.js`·`q.html`에 동의·고지 문구, 개인정보처리방침 링크가 없다. 받는 항목은 이름·휴대폰·지역(주소)·집 내부 사진이다. 하단 문구는 "입력하신 정보는 이 업체에만 전달됩니다." 한 줄뿐.
- **왜 문제인가**: 개인정보보호법상 수집할 때 목적·항목·보유기간을 알려야 한다. 처리방침은 "업체가 처리자, 회사는 수탁자"라고 적어 두었지만, 고객이 보는 화면에는 업체 이름도 처리방침도 연결돼 있지 않다. (정확한 법적 요건은 `legal` 담당 또는 전문가 확인 필요 — [추정])
- **고치는 법**: 마지막 단계(제출 버튼 바로 위)에 "수집 항목 / 목적: 견적·일정 안내 / 보유: 견적 후 ○개월 / 처리자: {업체명}" 4줄 + 처리방침 링크 + 동의 체크. 요청 문서에 `consentAt` 저장, 규칙에서 필수로.
- **난이도·시간 [추정]**: 낮음 · 0.5일 (+문구 법률 검토)

### ③ 로그인 없는 쓰기에 남용 방지가 없다 (비용·알림 폭탄) — [확인]
- **현상**
  - `requests` 생성은 형식만 맞으면 누구나 무제한. 업체 ID(=사장님 uid)는 견적 링크에 그대로 보인다.
  - 요청마다 고객 화면이 `notifyRequest`를 부르므로 **스팸 요청 1건 = 사장님 휴대폰 알림 1건.** 1순위 기능인 알림이 오히려 공격 통로가 된다.
  - Storage 규칙은 업체가 존재하는지만 본다. `requests/{shopId}/{아무 ID}/{아무 파일}`에 3MB 이미지를 무제한으로 올릴 수 있다. 요청 문서와 연결되지 않아 **고아 파일**이 쌓이고, 지울 수단도 없다.
  - App Check 없음, CSP 헤더 없음. 함수의 Origin 검사는 브라우저 밖(curl)에서는 위조된다.
- **고치는 법 (순서대로)**
  1. Firebase **App Check**(reCAPTCHA Enterprise) 켜기. Firestore·Storage·Functions에 적용. 코드 10줄 내외.
  2. 업로드 순서 바꾸기: 요청 문서 먼저 생성 → 사진 업로드. Storage 규칙에서 `firestore.get(requests/{requestId}).data.shopId == shopId && status == 'new'` 확인, 10분 안에만 허용.
  3. `notifyRequest`에 업체별 분당 알림 상한(예: 10분에 5건 넘으면 묶어서 1건).
  4. Storage 버킷 수명 주기 규칙(예: 180일 지난 `requests/` 자동 삭제) — ④와 같이.
  5. GCP **예산 알림** 설정 [미확인: 이미 했는지 콘솔 확인 필요].
- **난이도·시간 [추정]**: 중간 · 1.5~2일

### ④ 고객 사진·연락처를 지우는 장치가 없다 (개인정보·보관 비용) — [확인]
- **현상**: 실제 요청의 사진을 지우는 코드는 없다. `deleteObject`는 테스트 데이터 지우기에서만 쓴다(`owner.js:397`). 처리방침 7항은 "목적이 달성되면 지체 없이 파기"라고 적었는데 그렇게 동작하는 코드가 없다.
- **고치는 법**: 매일 도는 서버 함수 1개. 견적 후 N개월(예: 6개월, 처리방침과 맞춤)이 지난 요청의 사진과 `customer.phone`을 삭제하거나 가림. 계정 삭제 요청 처리도 같은 함수로.
- **난이도·시간 [추정]**: 낮음~중간 · 1일

### ⑤ 공개 요금 페이지가 실제와 다르다 (표시·광고, PG 심사) — [확인]
- **현상**
  - `pricing.html`은 월 요금제 3종(19,900 / 49,000 / 99,000원)과 "매월 카드 자동결제"를 안내한다. 그런데 결제는 미개통이고(`tossClientKey: ''`), **요금제별 기능 차이를 막는 코드가 없다.** 일정·직원 기능은 요금제와 상관없이 누구나 켤 수 있고(`scheduleOn`), "직원 수·견적 수 확대"는 **늘려줄 한도 자체가 없다.**
  - "청소·이사·에어컨·커튼·중문 등" "여러 업종 템플릿 사용"이라고 적었지만 운영 중인 업종은 1개(+시범 1개)다.
- **원인**: PG 심사용 페이지를 먼저 만들면서 설계도 12장의 계획을 그대로 옮김. 11-11 점검 결과 고친 뒤에도 남은 부분.
- **고치는 법**: 요금제를 **1종**(예: "무료 10건 → 월 19,900원")으로 줄이고, 업종은 "입주청소(운영 중), 도배(시범)"로 사실대로. 팀·회사 요금제는 요금제별 기능 제한이 실제로 생길 때 다시 올린다.
- **난이도·시간 [추정]**: 매우 낮음 · 1~2시간 (`pricing.html`, `terms.html`, `js/billing.js` PLANS)

> 순위 밖이지만 무거운 문제: **실사용 업체 0곳.** 코드 문제는 아니지만 위 5개를 합친 것보다 크다. 13장 우선순위 1번에 넣었다.

## 10. 경쟁 앱 대비 강점과 약점

**앞서는 부분 (사용자가 받는 결과 기준)**
1. **견적이 "분쟁 예방 문서"다.** 포함·불포함·추가요금 조건이 고객 화면에 구조화돼 나간다. 해외 도구는 견적=금액 목록이고, 숨고·카톡은 자유 문구다.
2. **한국 업종 규칙이 계산에 들어 있다.** 손 없는 날·음력 공휴일·주말 할증·평수 단가 (`calc.js` `dateFlags`).
3. **설치 없이 링크 하나.** 고객은 가입·앱 설치 없이 3분 입력. 사장님도 구글 로그인 한 번.
4. **고객을 뺏기지 않는다.** 숨고와 달리 견적마다 돈이 나가지 않고 고객이 사장님 것이다.

**뒤처지는 부분 (숨기지 않음)**
1. **검증이 없다.** 경쟁사는 전부 실사용으로 검증됐다. 이 제품은 0건.
2. **문의 입구가 약하다.** 고객이 링크를 눌러야 시작된다. 실제 문의는 전화·카톡·숨고로 온다 [추정]. 카톡 대비 "왜 링크를 눌러야 하나"를 고객에게 설득해야 한다.
3. **견적 이후가 끊긴다.** 계약금 입금·청구·영수증이 없다. Jobber·Housecall Pro는 견적→일정→청구→결제가 한 흐름.
4. **업종 1개.** 이사·에어컨 업체는 지금 시작할 수 없다.
5. **대체재가 공짜다.** 카톡 채널+전화+메모장이 무료라, "견적 시간 단축"을 숫자로 보여주지 못하면 19,900원을 낼 이유가 약하다.

## 12. 최종 추천 전략: A안 (최소 수정)

**선택 이유**
1. 지금 모든 판단의 근거가 없다. 다음 기능은 협력 업체 1곳의 실제 견적 10건을 보고 정하기로 이미 결정했다(CLAUDE.md 일하는 순서 규칙 2). A안은 그 10건을 **안전하게 받을 수 있는 최소 조건**이다.
2. A의 항목은 결제를 열기 전에 어차피 해야 하는 것(요금 우회, 남용 방지, 개인정보 고지·파기)이다. 나중으로 미룰 수 없다.
3. 평수 조회 제거로 코드가 줄어 이후 B안 비용도 내려간다.

**포기한 대안의 단점**
- **B안**: 지금 하면 "어떤 화면이 실제로 불편한지" 모르는 채로 다듬는다. `owner.js` 1,051줄은 불편하지만 장애는 아니다. 사용 데이터가 생기면 B의 일부(상세 화면 분리, 구독 범위)를 그때 고른다.
- **C안**: 위 11장.

**A안 다음 판정 기준 (끝났다는 기준)**: 협력 업체 1곳 · 실제 고객 견적 10건 발송 · 요청→발송 중간값 시간 기록 · 응답 누락 0건. 이걸 넘기 전에는 B·C 항목을 시작하지 않는다.
